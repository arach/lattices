Why it works

Users understand the core promise, then immediately see what else exists. The asymmetric grid makes Lattices primary and the companions clearly subordinate.

Cost

It adds a large section between the hero and the narrative proof. If it uses screenshots or long copy, it will read like a second landing page.

If used

Keep it typographic, link each card once, and let `/products` be the deeper browse surface. Do not restate the whole docs menu.

Why it works

It behaves like a table of contents for the ecosystem: short, scannable, and aligned with the site’s index-card texture.

Cost

It may not teach enough. A name plus one line can be skipped unless the user already knows they want another product.

If used

Treat it as navigation furniture, not a sales section. It can coexist with a later product story, but should not be the only explanation.

Why it works

Users learn the family at the exact moment a capability makes it relevant. This is the least marketing-shaped answer.

Cost

It is distributed, so nobody sees the whole family at once. It can also clutter sections if every product gets equal chrome.

If used

Use it as a product attribution layer. Pair with one dedicated family surface or `/products` so the full set is still discoverable.

Recommendation

Lead with A. Keep C as section metadata.

A dedicated module earns attention right after the hero without depending on the dropdown. Contextual callouts can then clarify which product owns each capability deeper in the page. The rail is a useful fallback if the module feels too heavy, but alone it likely undersells the family.

Primary

Family module after the hero — one clear map of Lattices + companions.

Secondary

Small product attribution chips inside relevant capability sections.

Fallback

Compact rail if the homepage needs to stay visually spare.
